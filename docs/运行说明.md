# 运行说明

本文面向作业负责人、存储平台值班与分析用户，说明如何把合成的执行记录转成
可消费的数据湖分区，以及失败重试、重复通知、迟到通知和部分输出各自由谁、
在何时、以什么方式处理。

> 所有资料均为本地合成数据。代码不会删除真实文件、访问网络或写入外部系统；
> 这里的“清理”仅指账本登记层面的规划与隔离。

## 1. 环境与约定

* Python 3.11–3.14，仅标准库。
* 时间统一为 UTC，输入可带 `Z` 后缀或显式时区。
* 未识别的枚举值不会被静默当成正常值，而是映射为 `unknown` 并登记异常。
* 字段定义见 `docs/资料契约.md`。

安装到当前环境（可选）：

```sh
python3 -m pip install -e .
```

未安装时设置 `PYTHONPATH`：

```sh
# Linux / macOS
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli inspect

# Windows PowerShell
$env:PYTHONPATH="src"; python -m compute_output_lake_commit_ledger.cli inspect
```

运行测试：

```sh
python3 -m unittest discover -s tests -v
```

## 2. 角色与职责

| 角色 | 职责 | 对应接口 |
| --- | --- | --- |
| 作业负责人 | 确认一次重跑是否代表新实验版本；补充说明 | `confirm_version`、`--confirm` 文件 |
| 存储平台 | 决定何时把输出标记为可见；处理提交恢复 | `commit`、`recover`、`quarantine`、`supersede` |
| 分析用户 | 依据提交账本选择可消费快照；查询引用 | `select_snapshot`、`references_*` |
| 调度/工作进程 | 上报完成、失败、重试通知 | `register_receipt` |

## 3. 装载资料

```sh
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli inspect
```

输出包含两部分：

* `reconcile`：输出/回执的匹配数量与标签偏移统计；
* `summary`：账本计数、分区状态、尝试终态、合格尝试与异常清单。

当前合成资料的典型结果：160 条输出、90 条回执全部匹配；输出标签相对真实作业
整体 +1（159 条），回执整体 +1（90 条）。装载器按 `(attempt, 日期)` 与时间
距离做确定性归属，并登记 `labels_reconciled_by_time` 与 `idempotency_key_reused`
两类异常。原始 `job_id` 标签保留在 `source_job_id` 字段中便于追溯。

### 为什么不用 job_id 直接关联

`output_objects.csv`、`completion_receipts.csv` 的 `job_id` 与 `jobs.csv` 的同名
作业在 `attempt` 和时间上不一致；若直接连接会得到 0 条匹配，或把输出记到错误的
尝试上。装载器只在“同一尝试序号、同一自然日、时间相差不超过 6 小时”的唯一候选
存在时才归属，否则登记 `unmatched_output` / `unmatched_receipt` 异常，不猜测。

## 4. 完成通知的幂等与迟到处理

`register_receipt` 在 `(job_id, attempt, idempotency_key)` 作用域内去重：

* 同一幂等键、同一类型的重复通知 → `duplicate`，仅留档。
* 同一幂等键、不同类型 → `conflict_ignored`，登记 `idempotency_conflict`。
* 不同幂等键但同类型成功通知 → `late_ignored`/`duplicate`，不重复生效。
* 已成功后再收到失败通知 → `late_ignored`，**不撤销**已提交版本。
* 失败之后收到成功通知 → `applied`，该尝试最终完成。

> 合成资料中 25 个幂等键被两个不同作业尝试复用（如 `IDEM-001`）。因为它们
> 落在不同尝试上，按尝试作用域分别幂等，不会被误判为重复通知；装载器登记
> `idempotency_key_reused` 提醒上游修正键生成。

## 5. 作业负责人确认重跑版本

每次装载后，不同指纹的重跑默认标记为“待确认重跑”，不可提交。负责人需要准备
确认文件，例如：

```json
[
  {
    "logical_run": "RUN-021",
    "version_id": "RUN-021:V2",
    "confirmed_by": "负责人甲",
    "is_new_experiment": true,
    "note": "新参数与新代码构成新实验版本"
  }
]
```

* `is_new_experiment: true` → 成为可提交的“重跑版本 #N”。
* `is_new_experiment: false` → 判定为同一实验的重复执行，保持不可见，
  提交原因码为 `version_declined`。

也可以按作业或指纹确认：

```python
ledger.confirm_version(
    "RUN-021", job_id="JOB-0066", confirmed_by="负责人甲",
    is_new_experiment=True, note="新参数",
)
```

传入 `--confirm 文件路径` 即可让后续命令应用这些确认：

```sh
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli \
  --confirm confirmations.json partitions
```

## 6. 提交完整性

提交前可用 `evaluate`（CLI 中体现在 `commit` 的返回）查看原因码：

| 原因码 | 含义 |
| --- | --- |
| `job_state` | 任务状态不是 `complete` |
| `no_outputs` | 没有输出对象 |
| `outputs_pending` | 有 `pending`/`unknown` 对象 |
| `outputs_partial` | 有 `partial` 对象 |
| `missing_success_receipt` | 没有终态或终态不是成功 |
| `receipt_failure` | 终态为失败 |
| `version_unconfirmed` | 重跑版本尚未确认 |
| `version_declined` | 负责人判定不是新版本 |
| `attempt_superseded` | 同版本已有更新的可见尝试 |
| `partition_quarantined` | 分区被隔离 |

### 当前合成资料的可提交结果

在确认 `RUN-000`、`RUN-021`、`RUN-033` 的重跑版本后，有三条尝试满足提交完整性：
`JOB-0090`、`JOB-0066`、`JOB-0078`（均为对应逻辑任务的 `attempt=3`）。其余尝试
要么任务未完成、要么存在未完成输出或缺少成功回执，均不能提交。

## 7. 提交与可见性

```sh
# 提交单个尝试（不满足完整性会返回 ok=false 与原因）
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  commit RUN-021 3

# 列出分区与可见性
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json partitions
```

* 提交成功后分区为 `committed`，携带凭证 `certificate`：作业、逻辑任务、尝试、
  代码版本、输入快照、参数哈希、资源队列、版本标识、对象数、总字节与输出摘要。
* 重复提交同一尝试返回 `action=verified`，不会产生第二个分区。
* 同一实验版本中更新的尝试提交后，旧尝试分区转为 `superseded`，其凭证清空，
  但分区与历史仍保留。
* 隔离（`quarantine`）会清空凭证并记录原因，分区不再对下游可见。

## 8. 提交恢复

存储平台在重启或对账后运行：

```sh
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json recover
```

`recover` 对存储快照逐条判定：

| 存储记录状态 | 账本事实 | 结果 |
| --- | --- | --- |
| `committed` | 满足完整性 | `verified`，补全凭证 |
| `committed` | 不满足完整性，且无更新合格版本 | `quarantined`（隔离） |
| `committed` | 不满足完整性，但同版本有更新合格分区 | `superseded`（被取代） |
| `staging` | 满足完整性，`auto_commit=True` | `promoted`（提升为可见） |
| `staging` | 不满足完整性 | `held`（保持暂存并记录原因） |
| `quarantined` | 任意 | `kept_quarantined` |
| 未知状态 | 任意 | `held` 并登记 `unknown_commit_state` |
| 无存储记录但账本已提交且合格 | — | `verified` |
| 无存储记录、账本中合格 | `create_missing=True` | 补建并提交/暂存 |
| 找不到对应作业尝试 | — | `skipped` 并登记 `partition_without_job` |

重复执行 `recover` 是幂等的：已可见分区只会得到 `verified`，不会重复创建。
使用 `auto_commit=False` 可只做对账而不提升暂存分区。

### 当前合成资料恢复后的结果

确认三个重跑版本并恢复后：

* 3 个合格重跑尝试变为可见分区（其中 `RUN-000` 的分区由账本补建）；
* 27 个记录为 `committed` 但不满足完整性的分区被隔离；
* 24 个记录为 `staging` 但不满足完整性的分区保持暂存并记录原因；
* 其余记录为 `quarantined` 的分区保持不变。

## 9. 下游选择可消费快照

```sh
# 选择当前可消费快照（默认要求版本已确认）
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  snapshot --run RUN-021

# 指定版本序号（例如回看基线版本）
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  snapshot --run RUN-021 --version 1

# 直接按分区标识读取
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  snapshot --partition P-0066
```

`select_snapshot` 只在可见分区中选择：

* 默认排除未确认的重跑版本；
* 同日多版本时选择版本序号最大、尝试最大的分区；
* 分区不可见时抛出 `PartitionNotVisible`（CLI 返回 `error` 并以非零码退出）。

快照携带 `partition`、`job`、`version`、`certificate` 与对象清单，分析用户可据此
核验输出来自哪个代码版本与输入快照。

## 10. 引用查询与清理

### 引用

```sh
# 某对象被哪些结果引用
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  references --object result/30/00066

# 某分区、某逻辑任务的全部引用
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  references --partition P-0066
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  references --run RUN-021
```

引用通过 `artifact_manifests.csv` 与 `object_parts.csv` 的对象键数字后缀落到具体
输出对象；`result_refs.csv` 的 `valid`/`review`/`withdrawn` 保留原始含义。
`valid` 引用保护对象，`review` 引用使对象保持待复核，`withdrawn` 不提供保护。

### 清理

```sh
# 只生成计划（默认）
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli cleanup --run RUN-021

# 执行账本层面的清理（仍然不触碰真实文件）
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli cleanup --run RUN-021 --apply --yes
```

清理动作：

| 动作 | 含义 |
| --- | --- |
| `delete` | 未完成输出且无有效/待复核引用，可回收 |
| `quarantine` | 完整但未提交到可见分区，移入隔离而非删除 |
| `hold` | 仍被待复核引用、属于运行中尝试，或有效引用指向不完整对象 |
| `protect` | 属于已提交可见分区、被有效结果引用，或属于待提交的合格尝试 |

**清理部分输出时会跳过仍被有效结果引用的对象。** 如果有效引用指向的是不完整的
对象，账本会登记 `valid_reference_to_incomplete_object` 并保持 `hold`，交由人工
复核，绝不自动删除。

## 11. 状态保存与恢复

```sh
# 保存
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  state --save out/ledger.json

# 载入并查看摘要
PYTHONPATH=src python3 -m compute_output_lake_commit_ledger.cli --confirm confirmations.json \
  state --load out/ledger.json
```

保存内容包括作业、输出、回执（含处理结论）、引用、版本确认、分区与异常。
载入后可见分区、凭证摘要与版本确认状态保持一致；重复登记同一条记录不会产生
第二个分区。

## 12. 常见问题

* **为什么很多尝试不可提交？** 合成资料刻意混入了失败、重跑、部分写出和回执
  冲突。完整性检查按原因码逐项列出，而不是给出单一布尔值。
* **分区记录写的是 `committed`，为什么被隔离？** 存储侧记录可能来自崩溃前的
  半成品提交。只有通过账本完整性检查才保留可见；否则隔离等待清理。
* **同一逻辑任务能否有多个可见分区？** 不同实验版本可以各自可见（基线 + 已确认
  的重跑）；同一实验版本只保留最新尝试可见，其余为 `superseded`。
* **迟到失败会不会把已提交分区撤下？** 不会。成功终态具有粘性；迟到失败只登记
  `conflicting_terminal_receipts` 异常。
* **清理会删除文件吗？** 不会。`apply_cleanup` 只修改账本登记并回报动作，
  实际文件回收需由存储平台据此计划执行。

## 13. 合成数据的限制

合成资料中的执行表存在整体标签偏移、幂等键跨尝试复用、分区清单编号与对象清单
不一致等噪声，用于检验对齐与冲突处理逻辑。它们不代表真实平台的数据质量；
在生产环境中应先修正上游标签与幂等键生成，并把本工具的异常清单作为数据质量
监控的输入。
